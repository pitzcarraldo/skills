# Tech Spec Review Rubric

섹션별 상세 체크리스트, 안티패턴, 판정 기준. 리뷰 시 SKILL.md의 워크플로우와 함께 사용한다.

## 1. Summary (요약)

**목적**: 스펙 전체의 who/what/when/where/why를 3줄 내외로 압축.

**Pass 조건**
- 3~5문장 이내이다.
- "무엇을 만드는가" + "왜 만드는가"가 한 덩어리로 읽힌다.
- 외부 의존성(API, 서비스)이 있다면 언급된다.
- 스펙을 끝까지 읽지 않고도 리뷰어가 엘리베이터 피치를 말할 수 있다.

**안티패턴**
- 한 문장짜리 제목 반복: "X 기능을 개발합니다." → Needs work
- 배경·목표·계획이 섞여 한 문단이 10줄 넘어감 → Needs work
- 기술 용어만 나열되어 비엔지니어가 읽을 수 없음 (buy-in 목적일 때만 문제)
- 템플릿 placeholder 문장 그대로 남아 있음 → Missing

**좋은 예**
> "하단 탭(Bottom Navigation)을 사용자가 원하는 순서로 커스텀할 수 있게 한다. 서버 정렬 API는 이번 스코프에 포함하지 않고, 순서를 로컬에 저장·로드한다. 2.45.0 릴리즈에 포함 예정."

## 2. Background (배경)

**목적**: Context 제공. 왜 지금 이것을 하는가, 어떤 사용자 문제를 푸는가, 이전 시도가 있었다면 그 결과.

**Pass 조건**
- 문제 상황이 구체적 숫자·사례로 뒷받침된다. (예: "20대와 30대의 추천 탭 노출 수는 월 n만 차이")
- 이전에 비슷한 시도가 있었다면 그 결과와 지금 접근이 왜 다른지 설명한다.
- 읽는 사람이 "아, 안 하면 안 되겠네"라고 동의할 수 있다.

**안티패턴**
- "사용자 경험 개선을 위해" 같은 일반론 → Needs work
- 데이터·인용·링크 없이 작성자 추정만 나열 → Needs work
- Goals 내용을 Background에 미리 풀어놓음 (섹션 경계 흐려짐)

**체크 질문**
- 이 프로젝트를 안 하면 정확히 무엇이 나빠지는가?
- 왜 지금인가? (타이밍 근거)

---

## 3. Goals (목표)

**목적**: 이 프로젝트가 달성하려는 결과물을 불릿으로 나열. 성공 평가의 yardstick.

**Pass 조건**
- 불릿 포인트 형태 (산문 금지).
- 각 항목이 **검증 가능**하다. "개선한다"보다 "A를 B로 바꾼다".
- Measuring Impact 섹션의 지표와 1:1 대응된다.
- 3~7개 사이. 10개 넘으면 스코프가 흐려진다.

**안티패턴**
- "성능 개선", "UX 향상" 같은 측정 불가능한 문구 → Needs work
- Plan의 작업 항목이 Goals에 들어옴 (작업은 Plan, 결과가 Goals)
- 사용자 관점 결과와 엔지니어링 결과가 섞여 구분이 안 됨

**Lyft 예시 (Spot the Bot)**
- Disrupt monotonous Twitter feeds with fun, unexpected, on-brand images. (subjective)
- Integrate with Twitter and Dog API. (objective)

주관적/객관적 목표를 구분해 태깅하는 것도 권장.

---

## 4. Non-Goals (목표가 아닌 것)

**목적**: 스코프 고정. 리뷰어의 스코프 확장 시도를 사전 차단.

**Pass 조건**
- 불릿 포인트 형태.
- "의도적으로 하지 않는 것"이 명시됨. 단순 "다음 버전에서"가 아니라 "왜 이번에는 안 하는지" 근거가 있으면 더 좋다.
- Plan을 읽고 리뷰어가 떠올릴 법한 확장 제안 3가지 중 최소 1~2개가 이미 여기 나열돼 있어야 한다.

**안티패턴**
- "없음" 또는 섹션 생략 → **거의 항상 Needs work**. Non-Goals가 없는 스펙은 스코프 확장에 무방비.
- 사실상 모두가 안 할 것들 나열 ("화성 탐사는 포함하지 않음") → 의미 없음

**리뷰어 팁**: Plan을 읽고 "이것도 해야 하지 않나?"라는 생각이 드는 항목 → Non-Goals에 명시 권장.

---

## 5. Plan (계획)

**목적**: 어떻게 기술적으로 접근할지. 테크 스펙에서 가장 긴 파트.

**Pass 조건 (목적에 따라 다름)**

*buy-in 단계*
- 전체 아키텍처 다이어그램 또는 텍스트 설명이 있다.
- 핵심 의사결정 포인트와 고려한 대안들이 나열된다.
- 외부 시스템과의 상호작용이 명확하다.

*구현 직전 단계*
- 위 조건 + **로우레벨 디테일**: API 엔드포인트, 요청/응답 스키마, 에러 코드, DB 스키마 변경, 마이그레이션 순서.
- 기존 코드베이스의 어느 파일/모듈을 수정하는지 구체적으로.
- 시퀀스/데이터 플로우/ERD 다이어그램 중 최소 1개.

**안티패턴**
- 산문만 있고 다이어그램·코드 블록·표가 전혀 없음 → 구현 직전 단계라면 Needs work
- "적절히 처리한다", "최적화한다" 같은 비결정 표현 → Needs work
- 대안 검토 없이 단일 접근만 제시 (Other Considerations가 비어 있으면 더 의심)
- 결정 못한 부분을 숨김 — 차라리 옵션 나열이 낫다

**체크 질문**
- 다른 엔지니어가 이 Plan만 보고 착수할 수 있는가?
- 실패할 수 있는 지점이 명시되어 있는가?
- 마이그레이션·롤백 계획이 있는가? (기존 시스템 변경 시)

## 6. Measuring Impact (임팩트 측정)

**목적**: Goals와 매핑되는 구체 지표. 출시 후 성공 여부를 객관적으로 판단.

**Pass 조건**
- 각 지표가 **숫자 + 기한**을 포함한다. (예: "출시 2개월 내 MAU 20% 증가")
- Goals의 각 항목에 대응하는 지표가 있다.
- 측정 방법/대시보드/쿼리 출처가 명시된다. (어디서 숫자를 확인할지)
- 베이스라인(현재 값)이 기록되어 있다.

**안티패턴**
- "사용자 만족도 향상" 같은 비정량 지표
- 지표는 있는데 어떻게 측정할지 없음 → 실제로는 측정 안 될 것
- Goals에는 3개인데 지표는 1개만 → 나머지는 어떻게 평가?

**특수 케이스**: 내부 개발자 생산성 향상이 목적이면 "PR 머지 시간", "빌드 시간", "온콜 알람 수" 등 내부 지표도 허용.

## 7. Security, Privacy, Risks

**목적**: 악용 시나리오와 실패 모드의 사전 점검.

**Pass 조건**
- 외부 사용자 대상이면 인증/인가 설계가 명시된다.
- PII를 다루면 저장 위치·암호화·접근 권한이 명시된다.
- 장애 시 blast radius(얼마나 많은 사용자/서비스에 영향)가 추정된다.
- Rate limiting, 입력 검증, 멱등성 등 일반 위험 완화책이 해당하면 언급된다.
- 롤백/킬스위치 계획이 있다.

**안티패턴**
- 섹션이 "N/A" 한 글자로 채워짐 → 거의 항상 Needs work. 정말 N/A인 경우는 드물다.
- "인증은 기존과 동일" — 기존이 뭔지 링크/요약 필요
- 외부 API 키·시크릿을 어떻게 관리할지 누락

**체크 질문**
- 악의적 사용자가 이 기능으로 무엇을 할 수 있는가?
- 부분 실패(한 단계만 성공) 시 데이터 일관성은?
- GDPR/개인정보보호법 관련 데이터를 건드리는가?

---

## 8. Other Considerations

**목적**: 고려했으나 기각한 대안들. 동일 제안이 리뷰에서 반복되는 것을 방지.

**Pass 조건**
- 기각된 대안이 최소 1~2개 나열된다.
- 각 대안에 대해 **왜 기각했는지** 근거가 있다. (비용, 복잡도, 일정, 리스크)

**안티패턴**
- 섹션이 비어 있음 → 대안 검토 없이 단일 경로로 달린 것 아닌지 의심
- "고려했지만 적합하지 않음" — 근거 없음

---

## 9. Milestones (마일스톤)

**목적**: 작업 분할 + 날짜. Source of truth로 유지.

**Pass 조건**
- 구체적 날짜 또는 스프린트가 붙어 있다.
- Plan의 작업 단위와 대응된다.
- 코드 프리즈, QA, 릴리즈, rollout 등 배포 관련 이벤트가 포함된다.
- 의존성(다른 팀 작업 완료 등)이 있다면 표시된다.

**안티패턴**
- "ASAP", "2주 이내" 같은 모호한 표현
- 개발 일정만 있고 QA/릴리즈 일정 없음
- 과거 날짜인데 업데이트가 안 됨 → 리뷰 시 지적 필수

**좋은 예 (뱅크샐러드 원문)**
```
~ 9/25: BPL 컴포넌트 개발
9/28 ~ 9/29: 실험 변수, 로컬 변수 추가
10/5: 하단 탭 확장 가능한 구조로 리팩토링
10/20: 2.45.0 코드 프리즈
11/4: 2.45.0 Rollout
```

## 10. Open Questions (질문들)

**목적**: 미해결 설계/구현 질문. 리뷰어에게 답을 요청.

**Pass 조건**
- 각 질문이 **누구에게** 답을 원하는지 명시된다. (팀 또는 개인 지명)
- 질문이 구체적이다. "어떻게 해야 할까요?"가 아니라 "A안과 B안 중 어느 쪽이 나은가? A는 X 장점, B는 Y 장점이 있음."
- 답이 나오면 질문을 지우지 말고 answered 표시 + 결론을 남긴다.

**안티패턴**
- 섹션이 비어 있음 → 모든 것을 혼자 결정한 것인지, 고민이 부족한 것인지 의심
- 질문이 Goals/Plan에 있어야 할 미결정 사항 ("어떤 DB를 쓸지 아직 안 정함")
- 답 없이 오래 방치 → 리뷰 시 지적

---

## 횡단 점검 체크리스트

리뷰 마무리 전에 반드시 확인:

- [ ] Goals의 각 항목이 Measuring Impact에 대응 지표가 있는가?
- [ ] Plan에 등장한 외부 의존성(API, 서비스)이 Security에서 위험 평가되었는가?
- [ ] Non-Goals가 Plan을 읽고 떠오르는 스코프 확장 유혹을 차단하는가?
- [ ] Milestones의 작업 항목이 Plan의 작업 단위와 매칭되는가?
- [ ] 문서 전반에 "TBD", "?", "아마도" 같은 미결정 표현이 남아있지 않은가? 있다면 Open Questions로 이동.
- [ ] 마지막 수정일이 현재와 비교해 지나치게 오래되지 않았는가?
- [ ] 다이어그램/표/코드 블록이 최소 1개 이상 있는가? (텍스트만 있으면 Plan이 취약할 가능성)

## 판정 기준

- **Pass**: 체크리스트 80% 이상 충족, 블로커 없음.
- **Needs work**: 핵심 요소는 있으나 구체성·증거·매핑 중 하나 이상이 부족.
- **Missing**: 섹션이 비어 있거나 template placeholder 그대로, 또는 내용이 있어도 주제와 무관.
